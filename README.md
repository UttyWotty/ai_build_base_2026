# ai_build_base_2026

An AI operations copilot for manufacturing. It predicts equipment failures, traces each one through spare parts, suppliers, and customer orders, and drafts the actions for a person to approve.
Built for the AI Builder Cup 2026, Manufacturing track (Intelligent Operations and Industrial Efficiency).

## The problem

When a machine is about to fail, maintenance, stores, purchasing, and customer service each see one piece of the problem in their own system. The question that matters ("this spindle fails in about a day; do we have the bearing, and whose orders slip if we don't?") takes hours of calls to answer, while the warning window runs out.

## The approach

A sense, reason, act loop over governed operational data:
1. **Sense.** A failure-prediction model raises an alert with a lead time.
2. **Reason.** A Gemini agent investigates the alert with governed tools only: sensor evidence, spare part stock across plants, supplier delivery performance, and customer orders at risk.
3. **Act.** It drafts a work order, a parts action, and a customer-impact note for a person to approve.

The agent never writes SQL and never invents a number. Details and milestones are in `docs/plan.md`.

## Setup

Requires Python 3.11.

```bash
make setup      # creates .venv and installs the package with dev tools
make data       # generates and conforms both worlds, then the bridge (about 30 seconds)
make models     # trains the failure model and replays its alerts (about 20 seconds)
make test       # runs the test suite
make lint       # runs ruff and the code rule checks
make settings   # prints the model endpoint and data directories in effect
```

Per-machine settings go in `.env`, copied from `.env.example`. The Makefile loads it for every target.

## Models

Every language feature goes through `src/llm_gateway`, and one setting chooses the model:
- **`LLM_PROVIDER=gemini`** (default) uses Gemini through the google-genai SDK. Locally it needs `GEMINI_API_KEY`, a free key from aistudio.google.com. On Google Cloud it uses Vertex AI with the service account instead. `GEMINI_MODEL` picks the model.
- **`LLM_PROVIDER=local`** uses an OpenAI-compatible server such as `mlx_lm.server` at `LLM_BASE_URL`, serving `LLM_MODEL`. It is the offline fallback.

Command lines accept `--provider`, `--model`, and `--base-url` for one run, for example `make pdm-eval` or `.venv/bin/supply-eval-nl --provider local`. The unit tests use scripted models and never call a real one.

Component commands carry a prefix, for example `make pdm-predict`, `make pdm-ui`, `make supply-demo-offline`, and `make supply-ui`. See `docs/components/pdm.md` and `docs/components/supply.md`.

## Impact analysis

`make impact A=<alert id>` (optionally `AS_OF=2026-07-25T02:00`) answers what an alert means beyond the machine:
- **Spares.** Stock at the site and at the sister site, open orders, and the other open alerts queued for the same spare.
- **Supplier.** The governed `supplier_otd` metric over the last 90 days, with its SQL fingerprint, and the expected lateness.
- **Options.** Every way to get the spare (own stock, open order, air transfer, broker, new order), each priced as extra spend plus lost contribution, with the customer order lines due during the outage.
- **Worst case.** Downtime if the failure comes as soon as the fastest past alert of the same failure mode. Only outcomes already in the past are used.

On the default data, the spindle-bearing alert on US1-L2-01 at 2026-07-25 02:00 shows the problem the copilot exists for:

```
spare SP-1001 Spindle bearing set: 1 on hand at US1, queue [AL-US1-L3-01-2026072017, AL-US1-L2-01-2026072502]
supplier V10001: on time 66.1%, expected 2 days late (sql 59337a47eb2e9a5d)
* transfer      DE1           ready 07-27 02:00  extra   650  down  10.0 h  lost       0  orders at risk 0
  emergency_buy broker        ready 07-28 02:00  extra 9,700  down  10.0 h  lost       0  orders at risk 0
  open_order    SPO-US1-0061  ready 08-04 14:18  extra     0  down 190.3 h  lost  93,825  orders at risk 4
```

The bridge (`semantic/bridge/bridge.yaml`) links sites to supply plants, components to spares and suppliers, and lines to the customer parts they make. `make bridge` simulates each site's spares store from the plant's repair history and the suppliers' real delivery record in the supply world.

## Operations agent

The copilot is a Gemini agent built with Google's Agent Development Kit (ADK). `make ask Q="..."` asks it one question at the demo clock (`AS_OF`, default 2026-07-25 02:00), and prints the trace and the answer.

Its tools are governed and point-in-time: plant history is cut at the demo clock, and work order closures after it are hidden.

| Tool | What it returns |
|---|---|
| `list_open_alerts` | Alerts still waiting for a repair, earliest deadline first |
| `analyse_alert_impact` | The impact analysis above, as the agent sees it |
| `get_sensor_evidence` | Daily means of the failure mode's symptom sensors over 7 days, with normal ranges |
| `get_supplier_record` | Governed `supplier_otd` with its SQL fingerprint, and the expected lateness |
| `oee_summary`, `failures`, `work_order_history` | Plant history from the OEE engine |
| `propose_action_plan` | A proposal for a person to approve: work order, parts action, customer note. Nothing is executed |

Guardrails:
- **Proposals only.** A proposal takes its numbers from the impact report; the model only chooses an option and writes the notes. Proposals wait in `data/copilot/proposals.json` for approval.
- **Verified answers.** Every number in the final answer is checked against the tool results, and the run is marked verified only when all of them match.

`make eval` runs the eight scenarios in `evaluation/copilot/scenarios.yaml`: triage, the bearing conflict, the recommended plan, the sensor evidence, the supplier record, creating a proposal, the calm hydraulic-pump case, and plant history. It checks the tools called, required phrases, the number check, and the proposal.

## Ground rules

- **Synthetic data only.** Every dataset comes from a seeded generator in this repository. No real client or employer data, schemas, or names are used.
- **Reproducible.** `data/` is not committed. The same seed recreates the identical data on any machine.
- **Governed numbers.** Metrics are defined once in `semantic/`, and the language model only chooses among governed definitions.
